## What `husnisse_bench` measures

`husnisse bench 10` (the mod's own `BenchCommand.Lines`, called through the harness so the numbers
land in the assertion buffer). Every metric is one call, averaged over 10 passes, with one warm-up call
outside the clock:

| metric | what one call does |
|---|---|
| `index` | `ContainerIndex.InClaim` — the scene scan that gathers the claim's containers |
| `network` | `StorageRouter.NetworkCandidates(claim, containers)` — blacklist / network / not-a-deposit filter |
| `decide` | one `StorageRouter.Decide` per sample stack, against a candidate list gathered once |
| `refill` | `FlowScheduler.Refill(claim)` — the whole pass a 5 s reconcile tick runs (drops inside the claim, ground and deposit, queue filled) |

`refill` runs with the claim's queue cleared first, so it measures a refill from empty rather than the
cheap "already queued" path. The queue is cleared again at the end.

## The numbers

```
husnisse bench scene claim=-1553089021:2047 containers=200 network=200 samples=40 runs=10
husnisse bench metric=index   units=200 runs=10 avg_ms=3.932 max_ms=4.761
husnisse bench metric=network units=200 runs=10 avg_ms=1.258 max_ms=1.838
husnisse bench metric=decide  units=40  runs=10 avg_ms=13.011 max_ms=15.555
husnisse bench metric=refill  units=40  runs=10 avg_ms=20.431 max_ms=31.062
husnisse bench done queued_after_refill=39 (queue cleared)
```

Reading them:

- **One reconcile pass costs ~20 ms** at 200 containers and 40 stacks, i.e. **0.4 % of the 5 s tick**.
  The tick is not where a 200-chest base hurts.
- **The routing answer is the largest per-item cost**: 13 ms for 40 stacks ≈ **0.33 ms per stack**
  against a 200-container network, because `Decide` walks every candidate and allocates a candidate
  record per accepting chest. That is the number to watch when 0.6 adds machines to the same network.
- **Gathering the claim is 4 ms and filtering it 1.3 ms** — the linear scan the roadmap promised to
  keep until the benchmark said otherwise. It says keep.
- A second run the same day on the same build (12:45) measured 3.5 / 0.9 / 12.3 / 19.4 ms — the host is
  shared with the live server and another card's client gate, so treat ±20 % as noise, not signal.

## What the phase changed because of it

- `Refill` gathers the claim's containers **once** and shares the list with the drop scan and the
  deposit scan (`StorageRouter.NetworkCandidates(claim, containers)`), instead of `ContainerIndex`
  running twice per tick.
- A claim with no usable container now skips the world's `ItemDrop` scan entirely, which is the one
  cost that does not depend on the claim's size.

## The tripwire

`husnisse-03d-bench.cmd` asserts `metric=refill … avg_ms ≤ 100` — 5× the observed cost, a structural
tripwire rather than a performance gate (the rig's real frame-time gate lives in `perf-gate`). It also
asserts the scene really had 200 containers, 40 samples, and that the pass queued work
(`queued_after_refill ≥ 20`), so a green run cannot be an empty one.
